# 项目记忆模板

只在创建、审计或重整长期项目的盘上记忆时读取本文件。模板是候选结构，不是强制目录；先沿用仓库已有名称，删除不适用的字段。

## 控制面记录

在建立或迁移文档前，先记录采用的拓扑（A：`.project` 本地控制面；B：`.project` 独立文档仓库；C：workspace 控制面）、选择原因、负责追踪它的仓库，以及新 clone 或新 Agent 的入口。若代码仓库与控制面分属不同 Git 仓库，分别记录路径、当前提交和验证命令；不得把两个仓库的状态合并成一个模糊的“干净”结论。

拓扑改变时，建立一份 finding 或决策记录，列出迁移前后的唯一事实来源、保留在本地的材料、迁移日期和代码基线。迁移完成后，旧位置只保留指针，避免两个位置继续双写。

## 建立前先盘点

在写文件前回答：

1. 哪个现有文件会被 Agent 自动读取？它的作用域是什么？
2. 哪些事实是稳定规则，哪些是当前状态，哪些是证据/决策，哪些只是逐轮历史？
3. 哪些文件由脚本生成？生成命令和源数据在哪里？
4. 项目如何判定完成、失败、退化和“意外成功”？
5. 哪些未提交修改属于其他执行者？避免覆盖或把它们写成自己的成果。

如果已有文件承担相同职责，优先修订或链接，不创建第二事实来源。

## `AGENTS.md` / `CLAUDE.md` 最小模板

```markdown
# <项目名>：Agent 工作规则

本文件只放跨会话稳定、违反后会造成系统性损害的规则。
当前进度见 `<状态路径>`；命令见 `<handoff 路径>`；证据见 `<findings 路径>`。

## 信任边界

- MUST：<必须真实验证或审阅的范围>。
- MAY ASSUME：<明确允许作为前提的边界>。
- 未列出的模拟、桩、生成数据或外部结论不得默认为可信。

## 成功判据

- `<工作类型>` 只有在 `<命令/审阅/外部状态>` 得到 `<期望信号>` 后才算完成。
- “命令运行完”“没有报错”“Agent 判断正确”不替代上述证据。
- 未运行的检查必须写“未验证”，并说明原因。

## 禁止事项

- MUST NOT：为通过检查而删除/跳过测试、降低阈值、放宽契约或改写期望结果。
- MUST NOT：静默扩大已确认范围，或把假设写成已确认事实。
- MUST NOT：覆盖不属于当前任务的未提交修改。
- <项目事故导出的其他禁令；每条链接到 finding 或原因>。

## 开始工作

1. 读取本文件、`<状态路径>` 和当前阶段资料。
2. 检查 Git/工作区、环境与最近验证证据。
3. 报告漂移、活动范围和真实阻塞；明确下一步时直接执行。

## 验证矩阵

| 变更类型 | 必跑检查 | 证据位置 |
|---|---|---|
| <类型> | `<命令>` | `<文件/CI/外部系统>` |

## 收工协议

1. 运行与变更匹配的验证和回归闸门；
2. 再生 `<生成文件>`，不得手改；
3. 更新 `<状态路径>`，结果绑定到 commit/版本/时间；
4. 追加 session 日志，必须包含失败尝试与原因；
5. 检查 findings/session 索引完整性，并写出一个可执行的下一步。
```

审查规则文件时，删除“写得很好”“保持高质量”“仔细测试”等不可检查的泛化要求。把反复出现但仍靠记忆执行的检查移入脚本或 CI，而不是继续加粗。

## `STATE.md` 最小模板

```markdown
# 当前状态

- 状态：active | blocked | complete
- 当前阶段/里程碑：
- 最近更新：<日期时间与时区>
- 代码/产物基线：<commit、版本或数据快照>
- 本轮工作区说明：<已有脏改动及归属>

## 已完成

- <结论> — 证据：<命令/产物/finding/用户确认>

## 进行中

- <工作单元> — 当前停点：<文件/步骤/观察>

## 尚未完成

- <按依赖或风险排序；不要复制完整 backlog>

## 阻塞事项

- <阻塞条件> — 需要：<用户决定/权限/外部状态/技术证据>

## 验证结果

| 检查 | 基于版本 | 最近运行时间 | 结果 | 证据 |
|---|---|---|---|---|
| `<命令>` | `<commit>` | `<时间>` | pass/fail/not run | `<路径>` |

## 下一步

1. 目标：<一个最小工作单元>
2. 命令/入口：`<可复制命令>` 或 `<文件:符号>`
3. 预期信号：<何时成功、何时停止>
4. 收工：<要跑的检查与要更新的文件>

## 交接备注

- <只记其他文档没有、但接棒者必须立刻知道的项目历史>
```

状态中写的是“最后一次已观察到的结果”，不是对当前工作树的永久保证。结果过期时显式标旧，不要假装仍然有效。

## Finding / 实验 / 决策模板

```markdown
# <稳定 ID>：<问题标题>

- 状态：hypothesis | confirmed | rejected | retracted | blocked
- 日期与环境：
- 影响范围：
- 关联提交/需求/事故：

## 问题

<什么现象需要判定；不要先写结论。>

## 假设与风险方向

<可能解释；如果误判，是假阳性、假阴性、数据损坏还是范围漂移？>

## 最小复现或判定方法

```sh
<可重放命令>
```

预期对照：<应成功与应失败的信号>。

## 观察

<原始结果的摘要与证据路径；注明版本和环境。>

## 结论

<只写证据支持的强度；否则保留“尚未判定”。>

## 影响与后续

- <规则、实现、闸门、状态或文档应如何改变>
- <仍未覆盖的分支>

## 来源

- <规范/代码/外部资料的版本、坐标和查询日期>
```

若结论被推翻，保留全文，并在标题下加醒目的推翻块：何时、被哪份新证据推翻、哪些旧结论不可再用。

## Session 日志模板

```markdown
# <日期/会话号>：<本轮主题>

## 目标
- <本轮承诺的最小范围>

## 做了什么
- <实际变更；链接到 commit/文件/finding>

## 验证
- `<命令>` → <结果>；基于 <commit/版本>
- 未运行：<检查>，原因：<原因>

## 失败尝试与原因
- <尝试> → <观察> → <为何不继续；证据在哪里>

## 决定与假设
- <谁决定、依据、影响；未确认项不得写成定案>

## 未完成与阻塞
- <准确停点和恢复条件>

## 下一轮入口
- `<第一条可执行命令>`
- 预期：<结果或停止条件>
```

Session 只追加历史，不作为当前真相来源。若日志结论影响后续决策，把它提升为 finding，并让 `STATE.md` 链接过去。

## 文档健康检查

只有项目初始化时启用了文档健康检查，才执行本节。规则文件或状态文件必须写明触发方式：例如每次里程碑切换、每 5 个工作单元，或每周一；“定期”单独出现不算有效配置。

检查：

- 规则文件是否混入了过期数字和临时计划；
- `STATE` 是否能在几分钟内读完，下一步是否真的可执行；
- 生成文件是否能从源数据重建，人工副本是否已消除；
- findings 与 sessions 的索引是否覆盖磁盘上的所有条目；
- 被推翻的结论是否仍可能被搜索结果误用；
- 最近验证是否绑定到明确版本，是否因未提交改动而过期；
- 每条高代价事故是否已经变成闸门、禁令、探针或显式限制；
- 启动 prompt 中的路径和命令是否仍存在。
